## Acceptance criteria

- [x] An event is created with the timezone option off by default; the organizer can enable, change, or disable it afterwards. — `Event.Create` sets `new EventParams(null)`; `UpdateEventParamsTests` verify enable/change/disable and persistence via `Params.Timezone`.
- [x] The participant's timezone is always captured (frontend always supplies it), even when the event's timezone option is off. — `JoinEvent`/`SetAvailability` both require + persist timezone regardless of `events.timezone`; `JoinEventTests.Execute_ShouldJoinNewParticipant` asserts the stored timezone on a passcode-protected, option-off event.
- [x] Availability submitted in a participant's timezone is stored as the correct absolute instants. — `SetAvailabilityTests.Execute_ShouldStoreUtcInstantsAndReturnWallClock` asserts Berlin 09:00–10:00 is stored as UTC 07:00–08:00.
- [x] With the option on, availability is returned converted into the viewer's timezone (participant B sees A's 18:00–20:00 in B's local time). — `GetEventAvailabilitiesTests`/`GetParticipantAvailabilityTests` assert a 12:00 UTC instant renders as 21:00 Asia/Tokyo when viewed from Tokyo.
- [x] Reads return the timezone label alongside the ranges, and fall back event timezone → UTC when the viewer has none. — `*_ShouldFallbackViewerToEventToUtc` tests assert viewer→event→UTC frame resolution and the returned label.
- [x] With the option off, reads return raw instants (legacy behavior). — `Execute_ShouldReturnParticipantsWithEmptyRangesWhenNoAvailability` and `Execute_ShouldReturnEmptyRangesWhenNone` assert `UTC` label + no conversion when the option is off.
- [x] A submitted range that cannot be interpreted unambiguously is rejected. — `TimezoneConverterTests` (DST gap/ambiguous) and `SetAvailability`'s `ParseWallClock` (malformed/offset-bearing → `invalid_availability_range`) cover this.
- [x] Enabling the option later requires no backfill; existing null-timezone participants still work. — No migration (confirmed via `has-pending-model-changes`); null `events.timezone` reads as UTC (legacy) and participant timezones are captured from first submit; the model delta is zero.

## Spec conformance

The change activates the dormant `events.timezone`/`participants.timezone` scaffolding and satisfies FR-001–FR-004 and US-001–US-004 as required: timezone option off by default and toggleable (FR-001), per-participant timezone always captured on join + availability-submit (FR-002), canonical UTC storage (FR-003), and viewer-timezone rendering with the viewer→event→UTC fallback and a returned label (FR-004). NFR-001–NFR-003 hold: the backend owns all conversion, wall-clock strings are unambiguous on the wire, and enabling the option later requires no migration/backfill (existing null-timezone rows remain valid). The two `Docs/specs/events/` and `Docs/specs/availability/` feature specs are still the pre-change truth and will be updated at fold time — no conformance gap exists in the implementation itself.

## Design conformance

All design decisions are followed: D1 (IANA ids, wall-clock `string`/`DateTime` on the wire, no raw offsets), D2 (`events.timezone` null = off via `EventParams`, `PUT /events/{publicId}/params` full-replace with organizer-only `X-Guest-Id`), D3 (timezone captured at join and at availability-submit), D4 (write wall-clock→UTC via `TimeZoneInfo.ConvertTimeToUtc`; read UTC→wall-clock; fallback chain; `invalid_timezone`/`invalid_availability_range` vs inline `BadRequest` split), D5 (no migration; invariants now measured on canonical UTC), D6 (new endpoint + `invalid_timezone` code; reads changed GET→QUERY via `MapMethods`). Minor deviations, both non-breaking: `EventParams` is a `readonly record struct` (vs `record` class); and the `UpdateEventParams`/`TimezoneConverter` DI registrations were physically introduced during Task 6 rather than Task 8 (user-approved, outcome identical). The generated TS client's `dist/`/`src/generated/` are gitignored by pre-existing convention, so the "commit dist" instruction is a no-op under the repo's publish-time-regeneration workflow.
