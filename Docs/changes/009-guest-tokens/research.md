# 009-guest-tokens: Research

## Tech stack

.NET 11 minimal APIs, EF Core + Npgsql (writes), Dapper over embedded SQL
(reads), PostgreSQL 18. xunit unit tests, Testcontainers integration tests,
Hurl scratch files for wire-level checks.

## Relevant modules

- `Features/Events/Api/EventsRestService.cs`, `Features/Availability/Api/AvailabilityRestService.cs`
  — every endpoint that needs "who is calling" parses `X-Guest-Id`, or reads
  `guestId` from the body (create/join/leave) or the query string (search).
- `Features/Events/Domain/GuestId.cs`, `Participant.GuestId` — the guest id is
  the only identity; `participants (event_id, guest_id)` is unique.
- `Features/Events/Application/{DeleteEvent,UpdateEventParams,LeaveEvent,JoinEvent}.cs`,
  `Features/Availability/Application/SetAvailability.cs` — organizer /
  ownership checks compare the caller's guest id to a participant's.
- `Features/Availability/Application/{GetEventAvailabilities,GetParticipantAvailability}.cs`
  — reads take no caller identity at all.
- `Common/ExceptionHandler.cs` — exception type → status + error code.
- `Composition/ServiceCollectionExtensions.cs` and
  `tests/FindAtime.IntegrationTests/Fixtures/IntegrationTest.cs` — two DI graphs.

## Existing patterns

- Feature slices `Api/Application/Domain/Infra`, typed ids, records for DTOs.
- Secrets are generated with `RandomNumberGenerator` (`PasscodeGenerator`) and
  only hashes are persisted (`PasscodeHasher`).
- Application exceptions mapped in one dictionary; bodies are `{ message, error }`.

## Feature spec summary

Events: a guest (identified by a per-browser UUID) creates an event and becomes
its organizer participant; others join (optionally behind a passcode) or leave;
only the organizer updates params or deletes. Availability: participants
replace their own ranges; anyone can read an event's availabilities.

The guest UUID is generated by the browser and trusted blindly by the API: it
is a bearer secret that is sent in clear in query strings (logged), and anyone
who learns it becomes that guest. Availability reads require no identity, even
for passcode-protected events. Passcode attempts are not rate-limited.

## Open questions

- Keep existing browser identities working? → yes: adopt legacy guest ids once.
- Should availability reads require membership? → yes; the UI only shows
  availability after joining, so no UX change.
